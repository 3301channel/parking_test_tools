# 泊车入位精度问题分析与调参开发文档

| 项目 | 内容 |
|---|---|
| 版本 | v1.0 |
| 日期 | 2026-10-26 |
| 适用环境 | Autoware Universe（Humble）+ `planning_simulator` + `sample-map-planning` |
| 适用场景 | 仿真泊车入位测试、泊车规划参数调优 |
| 数据来源 | 本机源码 / 实际生效配置文件 / 4 次实测日志（详见附录 D） |

---

## 1. 问题描述

### 1.1 现象

在 `planning_simulator` 中通过 RViz 的 **2D Goal Pose** 指定泊车目标（一个点 + 朝向）后，存在以下现象：

1. 规划器输出了到车位的路径，车辆也执行了，但**最终停在停车框外或压线**；
2. 有时**泊车规划根本没被触发**，车辆按普通车道规划开到目标点附近即判定到达；
3. 有时**泊车路径算出来了却没有执行**，状态机在同一秒判定 `ArrivedGoal`。

### 1.2 影响

- 无法稳定复现和评估泊车算法效果；
- 调参时无法区分「算法问题」与「目标设置问题」，实验数据不可比。

## 2. 系统结构与数据流

### 2.1 泊车相关的两套机制（容易混淆，需先分清）

| 机制 | 触发方式 | 规划器 | 输出话题 | 是否需要倒车 |
|---|---|---|---|---|
| **A. 靠边停车（pull over）** | `goal_planner` 判断 `isStuck` 后启动 | `bezier` / `shift` / `geometric` / `freespace` 四选一 | 混入 `/planning/scenario_planning/trajectory` | 仅 freespace 支持 |
| **B. 泊车场景（parking）** | `scenario.type == PARKING` | `/planning/scenario_planning/parking/freespace_planner`（A\* / RRT\*） | `/planning/scenario_planning/parking/trajectory` | 支持 |

> **关键认知**：机制 A 的前三种规划器是纯几何方法（贝塞尔 / 横向平移 / 圆弧），**不依赖 A\* 节点**，产出的路径外观和 A\* 结果很像。因此在 RViz 看到“一条到车位的路径”**不能证明 A\* 泊车被触发**。

### 2.2 节点链路

```
RViz 2D Goal Pose
   ↓
mission_planner            → 生成 Route（lanelet 序列）
   ↓
behavior_path_planner
   ├── start_planner        → 起步（含 freespace 起步）
   └── goal_planner         → 接近目标时的 pull over
          ├── bezier / shift / geometric   （几何，无需 A*）
          └── freespace_pull_over          （1 Hz 异步线程，触发条件苛刻）
   ↓
scenario_selector          → 决定 scenario.type（LANE_DRIVING / PARKING）
   ↓  （PARKING 时）
parking_container
   ├── costmap_generator    → /planning/scenario_planning/parking/occupancy_grid
   └── freespace_planner    → /planning/scenario_planning/parking/trajectory
   ↓
planning_validator → velocity_smoother → control
   ↓
mission_planner 的 arrival_check → AutowareState: ArrivedGoal
```

### 2.3 关键话题（排查用）

| 话题 | 含义 |
|---|---|
| `/planning/scenario_planning/scenario` | `scenario.type` 是否为 `PARKING` |
| `/planning/scenario_planning/trajectory` | 最终执行的主轨迹（含几何 pull over） |
| `/planning/scenario_planning/parking/trajectory` | **只有 A\* 泊车才会出数据** |
| `/planning/scenario_planning/parking/is_completed` | 泊车是否完成 |
| `/localization/kinematic_state` | 实际停车位姿（用于算偏差） |

## 3. 根因分析

### 3.1 根本约束：Autoware 不认识“停车框”

规划器只有两个空间约束来源：

1. **lanelet 边界**（由 `margin_from_boundary` 约束）；
2. **占用栅格 / 障碍物**（`occupancy_grid`，来自 `costmap_generator` 或感知）。

地面白色停车线**不是 lanelet，规划器看不见**。若框周围没有物理障碍，规划器没有任何信息知道“框在哪”，此时你给的 Goal 点是唯一依据——而它只被当作**搜索锚点**。

> 结论：**空旷场地 + 只有地面标线**的场景，本身就不具备“精确停在框内”的观测条件。必须补齐 3.5 节的手段。

### 3.2 目标是锚点，不是落点

`goal_planner` 的 `goal_search` 会在锚点附近搜索 `modified_goal`：

| 参数 | 当前值 | 含义 |
|---|---|---|
| `forward_goal_search_length` | 40.0 m | 向前搜索范围 |
| `backward_goal_search_length` | 20.0 m | 向后搜索范围 |
| `goal_search_interval` | **2.0 m** | 候选点间隔 |
| `max_lateral_offset` | 1.0 m | 允许横向偏移上限 |
| `lateral_offset_interval` | 0.5 m | 横向偏移间隔 |
| `goal_priority` | `minimum_weighted_distance` | 选点策略（含 `lateral_weight: 40.0`） |

**2 米一个候选点，比一个标准车位（约 5 m × 2.5 m）还粗**，很容易跳过框中心。

### 3.3 目标搜索不检查障碍

| 参数 | 当前值 | 问题 |
|---|---|---|
| `occupancy_grid.use_occupancy_grid_for_goal_search` | **false** | 选点时**完全不检查该位置是否有障碍/压线** |

这是“停到压线或出框位置”的直接原因之一。

### 3.4 到达判定过宽

| 参数 | 当前值 | 文件 |
|---|---|---|
| `arrival_check_lateral_distance` | 1.0 m | `planning.launch.xml:31` |
| `arrival_check_longitudinal_undershoot_distance` | 1.0 m | `:32` |
| `arrival_check_longitudinal_overshoot_distance` | 2.0 m | `:33` |
| `arrival_check_angle_deg` | 45.0° | `:30` |
| `th_arrived_distance`（goal_planner） | 1.0 m | `goal_planner.param.yaml:5` |

车辆进入目标点**前方 2 m、横向 1 m、角度偏差 45°** 的方框并持续 1 秒即判到达。对泊车而言，这个范围远超车位尺寸——**“大概到附近”就算完成**。

### 3.5 速度过高

| 参数 | 当前值 | 换算 |
|---|---|---|
| `freespace_planner.waypoints_velocity` | **5.0 km/h**（≈ 1.39 m/s） | 单位是 km/h，源码 `create_trajectory` 中 `/3.6` 换算 |
| `goal_planner.pull_over.pull_over_velocity` | 3.0 m/s | ≈ 10.8 km/h |
| `pull_over_minimum_velocity` | 1.38 m/s | ≈ 5 km/h |
| `backward_parking_velocity` | -1.38 m/s | ≈ 5 km/h |

`freespace_planner` 输出的是**恒速轨迹**（文档明确“仅支持恒定速度”），5 m/s 的轨迹在终点前没有减速剖面，全靠控制器硬刹，**末端横向误差与过冲几乎必然**。

### 3.6 触发时序矛盾（导致“有时根本不泊车”）

`goal_planner_module.cpp` 中 freespace 规划启动条件：

```cpp
if (isStuck(...) && is_new_costmap && needPathUpdate(...)) {
    const auto freespace_path_opt = planFreespacePath(...);
}
```

- `isStuck` 要求**车辆已经卡住**（普通路径到不了目标）才启动；
- 而 `arrival_check` 在车进入目标前方 2 m 时就宣布结束。

**前者太晚、后者太早**，中间没有留给泊车执行的时间窗口。实测日志中多次出现：

```
11:47:45  Freespace planning completed
11:47:45  AutowareState: Driving => ArrivedGoal      ← 同一秒
```

以及整个第一次行程 39 秒内 `freespace_planner` 零输出（`Waiting for the vehicle to stop` 出现 0 次，说明当时 `scenario` 并非 `PARKING`，节点一直走 `reset()` 分支）。

## 4. 解决方案

### 方案 A：让目标搜索感知障碍并加密（治本，优先）

**文件**：`…/autoware_planning_config/config/scenario_planning/lane_driving/behavior_planning/behavior_path_planner/goal_planner/goal_planner.param.yaml`

| 参数 | 当前 | 建议 | 理由 | 风险 |
|---|---|---|---|---|
| `use_occupancy_grid_for_goal_search` | false | **true** | 选点时排除有障碍/越界位置 | 占用栅格噪声大时可能无解，需配合 `obstacle_threshold` |
| `obstacle_threshold` | 60 | 60~80 | 栅格代价阈值 | 过低会把膨胀区当障碍 |
| `goal_search_interval` | 2.0 | **0.5** | 候选点加密到半米才能命中框中心 | 计算量约 ×4，1 Hz 线程可能变慢 |
| `lateral_offset_interval` | 0.5 | **0.25** | 横向偏移更细 | 同上 |
| `max_lateral_offset` | 1.0 | 垂直车位 1.2 / 侧方 0.5 | 与车位类型匹配 | 过大可能选到隔壁车位 |
| `th_arrived_distance` | 1.0 | **0.3** | goal_planner 自身到达阈值 | 过小可能判不到达 |
| `parking_policy` | `left_side` | 按车位方向设 `right_side` | 决定靠哪侧 | 选错会停在错误一侧 |

### 方案 B：收紧到达判定

**文件**：`planning.launch.xml:30-34`

| 参数 | 当前 | 建议（第一步） | 建议（目标值） |
|---|---|---|---|
| `arrival_check_lateral_distance` | 1.0 | 0.5 | 0.2~0.3 |
| `arrival_check_longitudinal_undershoot_distance` | 1.0 | 0.5 | 0.3 |
| `arrival_check_longitudinal_overshoot_distance` | 2.0 | 0.5 | 0.3 |
| `arrival_check_angle_deg` | 45.0 | 20.0 | 10.0 |
| `arrival_check_duration` | 1.0 | 1.0 | 1.0（保持） |

> **必须分两步收敛**。一次性收到 0.2 而控制器横向精度不足时，状态机会一直停在 `Driving` 不结束。

### 方案 C：降低泊车速度（性价比最高）

| 文件 | 参数 | 当前 | 建议 |
|---|---|---|---|
| `freespace_planner.param.yaml` | `waypoints_velocity`（单位 **km/h**） | 5.0 | **2.0 ~ 3.0**（≈0.56~0.83 m/s） |
| `goal_planner.param.yaml` | `pull_over.pull_over_velocity` | 3.0 | **1.0** |
| 同上 | `pull_over.pull_over_minimum_velocity` | 1.38 | **0.5** |
| 同上 | `pull_over.parallel_parking.backward.backward_parking_velocity` | -1.38 | **-0.5** |
| 同上 | `pull_over.parallel_parking.forward.forward_parking_velocity` | 1.38 | **0.5** |

泊车入位建议 0.5~1.0 m/s。**这一类改动风险最低、见效最直接**，建议作为第一步验证。

### 方案 D：放大 A\* 终点容差

**文件**：`…/scenario_planning/parking/freespace_planner/freespace_planner.param.yaml`

| 参数 | 当前 | 含义 | 建议 |
|---|---|---|---|
| `lateral_goal_range` | 0.5 | 终点横向**总**容差（代码内 /2 作 ±） | 按 `(车位宽 − 车宽)/2` 定，通常 0.4~0.6 |
| `longitudinal_goal_range` | 1.0 | 终点纵向总容差 | 0.8~1.2 |
| `angle_goal_range` | 6.0 | 终点角度总容差（度） | 4~8 |

> 这三项是「精度 vs 可解性」的平衡点：**太小 → A\* 报 `Can't find goal`；太大 → 允许停歪**。不能只往小调。

### 方案 E：把车位变成规划器可见的约束

适用于空旷场地（周围无物理障碍）：

1. **地图侧**：在 lanelet2 地图中把车位建为 `parking space` / `area`，让 `margin_from_boundary` 真正约束车位边界；必要时开启 `mission_planner` 的 `allow_area: true`（当前 false）。
2. **仿真侧（推荐先做）**：在停车框边界布置少量静态障碍（`dummy_perception_publisher`），让占用栅格形成“围墙”，A\* 自然规整入位。此法对验证算法边界敏感度最直接。

### 方案 F：操作规范（零成本）

1. 落点选车位**几何中心**，箭头方向与车位**长轴一致**；
2. 不要设在车位入口或车道末端（否则车辆正向即可到达，`isStuck` 不成立，A\* 不启动）；
3. 设 Goal 前先用 **2D Pose Estimate** 精确对齐自车；
4. 一轮测试中进行过程中**不要重设 Initial Pose**，位姿跳变会导致 `Invalid start or goal pose` 与 `Invalid Trajectory`。

### 方案 G：闭环微调（工程兜底）

Autoware 无现成功能，需自建节点：

```
订阅 /planning/scenario_planning/parking/is_completed
  → 完成时读 /localization/kinematic_state
  → 与车位中心算横向偏差 / 角度偏差
  → 超阈值（如 lateral > 0.2 m 或 angle > 5°）则重新下发修正后的 Goal
```

## 5. 实施路线与验收

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| 1 | 仅实施方案 C（降速） | 同一目标重复 3 次，横向偏差标准差下降 |
| 2 | 实施方案 A（occupancy + 加密搜索） | 不再出现“车位被占仍选择该点” |
| 3 | 实施方案 B（分两步收紧到达） | 停稳后横向偏差 < 0.3 m，角度偏差 < 10° |
| 4 | 实施方案 E（车位建模） | 车完全在框内，四角不出界 |
| 5 | 方案 G（如需要） | 偏差超阈值时能自动重入位 |

**每次只改一个阶段**，否则无法归因。

## 6. 验证方法

### 6.1 量化指标

| 指标 | 计算方式 | 目标 |
|---|---|---|
| 横向偏差 | 停车位姿到车位中心线的垂距 | < 0.2 m |
| 纵向偏差 | 沿车位长轴方向偏差 | < 0.3 m |
| 角度偏差 | 车位长轴与车头朝向夹角 | < 5° |
| 是否在框内 | 车四角多边形 ⊆ 车位多边形 | 必须满足 |

### 6.2 检查命令

```bash
# A* 泊车轨迹终点是否在车位内
ros2 topic echo /planning/scenario_planning/parking/trajectory --field points[-1].pose.position

# 是否进入泊车场景
ros2 topic echo /planning/scenario_planning/scenario --field scenario.type

# A* 是否真的在出轨迹
ros2 topic hz /planning/scenario_planning/parking/trajectory

# 泊车完成标志
ros2 topic echo /planning/scenario_planning/parking/is_completed

# 实际停车位姿
ros2 topic echo /localization/kinematic_state --field pose.pose.position
```

### 6.3 日志判读（`freespace_planner` 的全部输出）

| 日志 | 含义 | 判读要点 |
|---|---|---|
| `initialize planning algorithm: astar` | 节点启动 | **不能**作为“进入泊车”的标志 |
| `Waiting for the vehicle to stop before generating a new trajectory` | 已激活但车在动 | 出现即证明 scenario = PARKING 且节点在工作 |
| `Freespace planning completed` | 规划成功 | 只代表路径生成，不代表执行完成 |
| `Can't find goal: <原因>` | 规划失败 | 常见 `Invalid start or goal pose` |
| `Course out` | 偏离已规划路径 | 通常由位姿跳变引起 |
| `Waiting for route data / occupancy grid / odometry` | 已激活但输入缺失 | 检查上游话题 |

> **判定“是否进入泊车模式”的可靠方法**：看 `/planning/scenario_planning/scenario` 的 `scenario.type`，或日志里是否出现 `Waiting for the vehicle to stop`。**不要**用 RViz 里是否有一条到车位的线来判断——那可能是几何 pull over 路径。

### 6.4 轨迹自动采集与评估（工具）

为避免每次手动 `ros2 bag record` + 人工测量偏差，已在 `start_planning_sim_log.sh` 中集成自动化链路。

**工作方式**

```
启动 → 后台 ros2 bag record（7 个关键话题）
Ctrl+C → 停止录制（SIGINT 保证 metadata 完整）
       → 自动调用 analyze_parking_session.py
       → 在本次日志目录下生成轨迹图与评估报告
```

**采集话题**

| 话题 | 用途 |
|---|---|
| `/planning/trajectory` | **最终主轨迹 —— RViz 上看到的完整路径**（评估基准） |
| `/planning/scenario_planning/parking/trajectory` | A\* 泊车段，**单向切分且点稀疏（实测仅 10 点 / 4.6 m）**，不能代表完整入库路径 |
| `/planning/scenario_planning/parking/is_completed` | 泊车完成状态 |
| `/planning/scenario_planning/scenario` | 是否进入 PARKING 场景 |
| `/planning/mission_planning/route` | 目标位姿 |
| `/localization/kinematic_state` | 起始与最终停车位姿 |
| `/perception/object_recognition/objects` | 周围车辆 |

**输出文件**（位于 `~/autoware_logs/<时间戳>/`）

| 文件 | 内容 |
|---|---|
| `trajectory_plot.png` | 轨迹平面图：前进段绿色 / 倒车段橙色、车位框、障碍物、起点/终点/最终位姿 |
| `trajectory_info.json` | 完整轨迹点、起点/终点、车位、障碍物、全部指标（机器可读） |
| `trajectory_points.csv` | 轨迹点表格（Excel 可打开） |
| `evaluation.md` | 人读报告：指标表 + 周围目标表 |
| `bag/` | 原始 rosbag，可用 `ros2 bag play` 复盘 |

**评估指标**

| 类别 | 指标 |
|---|---|
| 几何 | 轨迹总长、前进段长、倒车段长、方向切换次数（揉库次数）、绕行系数 |
| 平滑度 | 最大曲率、平均曲率、最小转弯半径、曲率抖动标准差 |
| 入位精度 | 终点相对车位中心纵向/横向偏差、角度偏差、是否在车位框内 |
| 最终位姿 | 停车后相对车位的纵向/横向/角度偏差、是否在框内 |
| 安全 | 最近障碍物距离、周围车辆数 |

**车位定义**：`parking_slot.yaml`

地图 `sample-map-planning` **未定义停车位**（无 parking 相关 lanelet），因此车位需手工配置：

```yaml
parking_slot:
  center: [3718.31, 73751.30]
  yaw: 1.93369
  length: 5.0
  width: 2.5
```

未配置时脚本退化为「Goal 点作为车位中心 + 默认 5.0×2.5 m」，报告中会明确标注来源。

**开关**

```bash
RECORD_BAG=0 ~/zzz/parking/start_planning_sim_log.sh      # 关闭录制与分析
SLOT_FILE=/path/to/my_slot.yaml ~/zzz/parking/start_planning_sim_log.sh  # 指定车位
```

**单独分析已有 bag**

```bash
source ~/autoware/install/setup.bash
python3 ~/zzz/parking/analyze_parking_session.py ~/autoware_logs/<时间戳>/bag \
        --out /tmp/out --slot ~/zzz/parking/parking_slot.yaml
```

**注意事项**

- bag 体积：轨迹话题 10 Hz，5 分钟约数十 MB ~ 数百 MB，长时间运行需注意磁盘；
- 轨迹帧选择：取**终点最接近最终停车位姿**的一帧作为入位轨迹（早期用“最长帧”会选到车道行驶段，终点离车位还有十几米，导致图与实际不符）；
- 图中同时叠加三要素：`planned corridor`（车位 12 m 内所有规划帧的点云，对应对 RViz 的蓝色走廊）、`executed (odom)`（实际行驶路径）、彩色线（选中的入位轨迹，前进绿/倒车橙）；
- 图中文字使用英文（避免容器内中文字体缺失导致乱码），指标名在 JSON/MD 中为中文。

## 7. 风险与回滚

| 风险 | 触发条件 | 应对 |
|---|---|---|
| 收紧到达判定后卡在 `Driving` 不结束 | 控制器横向精度不足 | 分两步收敛；必要时回退到 0.5 |
| `goal_search_interval` 过密导致规划超时 | 1 Hz 异步线程算不完 | 回退到 1.0；或减少 `forward/backward_goal_search_length` |
| 开启 occupancy 后无解 | 栅格噪声 / 膨胀过大 | 调高 `obstacle_threshold`；检查 `costmap_generator` 输出 |
| 降速后任务时间变长 | 长距离 pull over | 仅对泊车段降速，保持巡航速度不变 |

**回滚方式**：所有改动均为 YAML / XML 参数，改前备份原文件即可回滚；`autoware_planning_config` 若使用 `--symlink-install` 则改源码立即生效，否则需 `colcon build --packages-select autoware_planning_config`。

### C. 已知环境限制

本机 `rcl_interfaces` 仅含 6 个 srv，**缺少 `SetLoggerLevel` 定义**，因此：

- `ros2 service call … rcl_interfaces/srv/SetLoggerLevel` 会报 `The passed service type is invalid`；
- 节点上不存在 `set_logger_level` 服务，`rqt_console` 的动态调级别功能同样不可用；
- 需要 DEBUG 日志（如 `Freespace planning: x [s]` 规划耗时）只能：① 修改 launch 传 `--ros-args --log-level debug`；② 把源码中的 `RCLCPP_DEBUG` 改为 `RCLCPP_INFO` 后重新编译。
